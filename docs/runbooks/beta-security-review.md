# Focused beta security review · 2026-10-24

Scope: the Svelte portal's administrator, learner, profile, and completion-record workflows; Keycloak sign-in; the Moodle identity/evidence boundary; and the single-host staging/recovery configuration. The React visual reference is outside the deployed beta image. This is a source and automated-behavior review, not an external penetration test or approval to admit real participants.

The categories follow the [OWASP Top 10:2025 list](https://top10.owasp.org/2025/). Evidence below concerns this repository's controls, rather than a claim that a category is eliminated.

| Category | Reviewed controls and evidence |
|---|---|
| A01 · Broken access control | Actor, tenant, site, role, and learner/person scope are checked server-side in `auth.ts`, `people.ts`, `courses.ts`, `assignments.ts`, and `records.ts`. PostgreSQL integration tests exercise foreign tenants/sites, self-service restrictions, privileged mutations, and transcript/export access. Moodle rejects foreign tokens, unprovisioned identities, and mismatched OAuth bindings in real CI services. Cookie-authenticated mutations require the same origin. |
| A02 · Security misconfiguration | Production rejects synthetic authentication, validates private configuration, keeps databases private, and uses separate database roles. `request-security.ts` applies response headers and no-store behavior; `vite.config.ts` supplies CSP. Cookies are HttpOnly, SameSite=Lax, and Secure for HTTPS origins. Production startup CI verifies separate services and database connection isolation. Deployed ingress, TLS, trusted proxy configuration, and real SMTP still require chosen-host checks. |
| A03 · Software supply chain failures | Lockfiles and `npm ci` are used by CI and production image builds. Moodle 5.3.0 is checked against a fixed published SHA-256; the local extension is included in the reviewed image and recovery. The production web dependency audit reports zero vulnerabilities on this dependency set. Base-image registry trust, image updates, and the deployment account remain operator responsibilities. |
| A04 · Cryptographic failures | OIDC uses state, nonce, PKCE, issuer/audience checks, and an explicit signature algorithm list. Session cookies are signed; activation codes are stored as SHA-256 digests with expiry and single-use consumption. Backups are encrypted with age; CI demonstrates a restore with a separately held ephemeral key. Actual offsite storage, host secrets, and independent key retrieval remain open. |
| A05 · Injection | SQL uses bound parameters and validated IDs/filters. Dynamic schema/table identifiers in recovery are quoted and constrained by the recovery tool. CSV exports quote cells and neutralize spreadsheet formula prefixes. Svelte escapes profile and record text; native practice content comes from verified operator sources, and the GIFT answer key is outside the learner web root. |
| A06 · Insecure design | Moodle owns attempts, grading, progress, and source completion. A practice completion never creates workplace authorization. Course/version mappings and historical snapshots are immutable; manual completion provenance, correction, and void events retain originals. Enrollment and account changes share a person lock, and an uncertain late account creation keeps suspension retrying. Controlled database races and completion-history tests cover these boundaries. |
| A07 · Authentication failures | Keycloak supplies individual identities and privileged MFA. Stable sign-in identifiers are distinct from contact addresses; technical email is never marked verified. Activation consumes a one-time code before enabling access. Session-version and issue-time cutoffs reject revoked sessions/tokens. Sign-in, activation, account actions, and exports have bounded request limits. Real CI browsers prove password/OTP flows, exact Moodle account binding, and terminating a Moodle session. |
| A08 · Software or data integrity failures | Course source/export hashes, exact Moodle mappings, canonical course completion times, and append-only evidence preserve provenance. The source bridge reads completion and grade through Moodle APIs without writing tracking records. The full encrypted recovery rehearsal verifies all three databases, evidence lineage, files, ownership, restored credentials, and recovered service health. |
| A09 · Security logging and alerting failures | Consequential administrative actions are audited with actor, reason, and before/after values. Server requests and jobs have generated correlation IDs; unexpected errors log route templates and fixed metadata. Browser reporting accepts only a closed route/code/status vocabulary, limits payload size and traffic, and discards messages, stacks, full URLs, and identity fields. A local forced-job-failure webhook probe passes; real monitoring/alert ownership and recipient delivery remain open. |
| A10 · Mishandling exceptional conditions | Invalid bearer credentials return 401 through response finalization; provider/infrastructure failures receive a generic response without exception details. Typed and unexpected server failures retain request IDs and response protections. Browser reports have bounded retries/traffic and silent failure handling. Jobs retry with backoff; deactivation and uncertain provisioning cannot be labeled synchronized merely because no account was found once. |

## Findings and disposition

1. **Enrollment versus account revocation:** provisioning could overtake a completed no-account suspension. Fixed by shared person locking, atomic local success writes, and retrying uncertain account absence. Database tests deliberately pause provisioning and interleave deactivation/printed reset, and simulate a late remote account after timeout.
2. **Authentication exception boundary:** malformed bearer verification could bypass request finalization. Fixed by classifying invalid credentials and finalizing authentication/route failures. Focused tests inspect the actual malformed-token response and security headers, redirects, and sanitized 5xx failures.
3. **Missing browser diagnostics:** added bounded first-party reporting of fixed error metadata. Tests reject additional fields, full URLs, invalid encodings/oversize bodies, foreign origins, and excess traffic. No error object, message, stack, user identifier, or persistent browser identifier is sent.

The native Moodle course browser rehearsal and these new response/telemetry checks must pass on the final reviewed commit. CI results are linked from the draft pull request; a green synthetic run does not close the live gates below.

The [accessibility evidence record](beta-accessibility.md) explains the native Quiz's narrowly verified focus-guard disposition, retained raw axe findings and open human testing. An accepted focus guard is not a blanket exemption for hidden controls or a screen-reader acceptance result.

## Open release gates

- Verify HTTPS, ingress limits, proxy trust, secrets, isolation, and anonymous/authenticated responses on the chosen staging host.
- Confirm real invitation delivery and a named recipient for failures; exercise deployed monitoring and rollback.
- Verify offsite backups and independent decryption-key retrieval, with a measured recovery window.
- Complete a human keyboard and screen-reader pass, including the native Moodle assessment. Automated axe checks and keyboard-driven test responses provide separate evidence and do not substitute for this pass.
- Approve participant privacy/retention terms and course content, then complete the focused participant run.
