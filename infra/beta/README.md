# Beta deployment and recovery

The application image, migration step, worker, alert adapter, and recovery tools are implemented here. **Company IT will provide hosting; no staging host has been provisioned.** Use the [IT handoff](../../docs/runbooks/beta-it-handoff.md) to confirm the actual environment. Host/account, public DNS, service ownership, recurring cost, external alert recipient, managed backup/PITR configuration, chosen-host recovery, deployment, and rollback remain release checks. `infra/compose.yaml` is a disposable development fixture and must not hold participant data.

For one Linux server containing the application, sign-in, Moodle, and databases, use the separate [one server option](single-host/README.md). It uses one generated private settings file and optional automatic HTTPS. The externally hosted services configuration below remains available.

The deployable topology is a Linux Docker host for the Node application and worker, with separately operated PostgreSQL, Keycloak, Moodle, and file storage. `compose.yaml` deliberately requires the configured service endpoints. It does not create insecure default identity or Moodle services. Use TLS for every public endpoint and managed PostgreSQL connection, an ingress proxy on the application host, and a private network or restrictive firewall for service access. Add shared ingress limits for sign-in, invitations, and CSV exports when more than one application process is deployed; application limits alone are per process.

The pinned Node adapter reconstructs each request origin from the public `Host` and `PROTOCOL_HEADER=x-forwarded-proto`. The ingress must preserve the public portal Host and overwrite `X-Forwarded-Proto` from its trusted connection information. Keep the application port private/loopback; participant-supplied forwarded headers must not reach it unchanged. `APP_ORIGIN` defines application/OIDC callback URLs; the adapter no longer reads a runtime `ORIGIN` variable. Verify sign-in/callback and an actual activation/sign-out form POST through the final HTTPS ingress so its reconstructed origin matches the browser.

## Prepare a host

1. Record the host/provider, region, administrator, backup owner, on-call recipient and escalation contact, estimated monthly cost, retention, and restore objective in the staging release record. Confirm participant privacy terms before creating real accounts.
2. Provision a dedicated PostgreSQL database, Keycloak realm/confidential client, Moodle instance and data/code directories, and upload/media storage. Use the exact HTTPS callback `${APP_ORIGIN}/auth/callback`, individual identities, role-appropriate MFA and recovery, verified Moodle identities/cohorts, and narrowly scoped Moodle service credentials. Keep Moodle's database/code/files recovery points coordinated.
3. Generate the variables in `.env.example` through the host secret manager. Set `NODE_ENV=production` through the image; never set `DEV_AUTH`. Give the application DB account only application/migration privileges in its own database, and restrict administrative DB access. Test the required Moodle/OIDC paths before granting learner access. Backups use separate credentials and are never provided to the web container.
4. Supply secrets as a protected host env file (`chmod 600`) generated by the secret manager. Set `BETA_ENV_FILE` to its absolute path and `BETA_STATE_DIR` to a protected directory outside the checkout. The deploy script also needs `ALERT_OWNER` and `ALERT_WEBHOOK_URL` in its process environment so a failed deployment can alert. Configure the webhook integration to route the JSON event to that named person and test receipt.
5. Build and push both targets from the repository root in CI, using the reviewed commit SHA as an immutable registry tag:

   ```sh
   docker build --file web/Dockerfile --target runtime --tag "$BETA_IMAGE_REPOSITORY:$BETA_IMAGE_TAG" .
   docker build --file web/Dockerfile --target tools --tag "$BETA_IMAGE_REPOSITORY:$BETA_IMAGE_TAG-tools" .
   docker push "$BETA_IMAGE_REPOSITORY:$BETA_IMAGE_TAG"
   docker push "$BETA_IMAGE_REPOSITORY:$BETA_IMAGE_TAG-tools"
   ```

   `web/Dockerfile.dockerignore` excludes secrets and generated files from this root build context. The application image contains production dependencies; the tools image retains the locked TypeScript runner for migrations and jobs. CI must run existing checks before invoking deployment. Registry credentials belong in CI/host secret storage. An ingress proxy terminates HTTPS and forwards to the loopback-bound port 3000; it must preserve the configured public origin. Configure request/body limits and independent uptime checks for `/api/health`.
6. Deploy with `sh infra/beta/deploy.sh "$BETA_IMAGE_TAG"`. It pulls the immutable images, runs migrations before changing the web service, waits for database-aware readiness, then starts scheduled Moodle outbox processing and reconciliation. Publish no participant-facing URL until authenticated smoke tests, cross-site/tenant denials, Moodle sign-in, resume/retry/score capture, and accessibility checks pass on this host.
7. After a second healthy deployment, `sh infra/beta/deploy.sh --rollback` selects the prior successful application image without re-running migrations. Schema changes must remain compatible with that image. Destructive migrations require a separate maintenance/recovery plan. Exercise this rollback once on staging and save the output; source availability does not prove rollback works.

## Jobs and alert delivery

The worker processes the Moodle outbox (including user suspension/reactivation) and reconciles completions every five minutes by default, with structured run IDs. Advanced reassignment automation is outside the focused beta and is not scheduled. The worker posts `hse.jobs.failed` or recovery events to `ALERT_WEBHOOK_URL`, including `ALERT_OWNER`. Missing alert configuration prevents worker startup. A non-2xx/timeout/redirect fails delivery; `alert.delivered` is emitted only after a successful HTTP response. The once/probe commands return 1 for a reported job failure and 2 when the alert could not be delivered. The host must monitor worker/container restarts and `alert.delivery_failed` independently so a broken webhook is observable.

```sh
# Local synthetic verification only; does not contact the actual recipient.
node infra/beta/verify-alert.mjs

# On staging, use the real configured hook and confirm the named person received it.
node infra/beta/run-jobs.mjs --probe-failure
```

Schedule an independent uptime monitor against HTTPS `/api/health`, browser/server error monitoring, and host alerts for disk capacity, database backup/PITR failures, failed deploys, expired credentials/certificates, and failed alert delivery. `notify.mjs hse.uptime.failed` is the webhook adapter for a failed external probe. No reminder job is scheduled because reminders are outside this beta scope.

## Back up the complete recovery set

Use PostgreSQL client tools matching or newer than the server, Python 3.9+, and `age`. Put the age private identity in separate protected recovery storage; the backup host needs only the public recipient. Run daily full backups and enable managed PostgreSQL point-in-time recovery with a retention window accepted by the owner. Upload encrypted archives to a separate protected storage account with lifecycle retention and restore access. These service-side settings still need provisioning; local SQL dumps do not provide PITR.

Provide the following through a separate backup secret context:

- `HSE_DATABASE_URL`, `KEYCLOAK_DATABASE_URL`, `MOODLE_DATABASE_URL` (each database independently);
- `MOODLE_FILES_DIR` (all persistent Moodle data/course files), `MOODLE_CODE_DIR` (exact installed core, config and extensions), `HSE_UPLOADS_DIR` (all app/media/uploads or a verified object-storage export directory);
- `AGE_RECIPIENT` (the public recovery recipient), and `BETA_BACKUP_QUIESCED=yes` after stopping writes.

Put the app into a maintenance window, stop workers, enable Moodle maintenance, and pause upload writes before confirming the quiesced flag. Each database dump uses an exported repeatable-read snapshot; the maintenance window makes the three service snapshots and filesystem copies consistent with each other. Keep it short and record the recovery point and any writes that require replay. For large datasets use coordinated provider snapshots instead and prove they restore equivalently.

```sh
python3 infra/beta/recovery.py backup --output /protected-backups/hse-beta-2026-10-24.tar.age
```

The command encrypts the three custom-format dumps, file archives, checksums, table counts, and a digest of one HSE evidence record with linked amendment/audit facts. It keeps temporary plaintext in a private directory and removes it on exit. It refuses overwrite and symlink-dependent file trees. Alert on a nonzero exit and a missing expected daily archive. Rotate application/identity/Moodle secrets according to the host policy; backups contain sensitive configuration and require controlled access.

## Restore into isolation

Precreate three **empty** databases and an empty filesystem destination on a separate recovery environment with no outgoing learner messages. Set `RESTORE_HSE_DATABASE_URL`, `RESTORE_KEYCLOAK_DATABASE_URL`, `RESTORE_MOODLE_DATABASE_URL`, `AGE_IDENTITY_FILE`, and `BETA_RESTORE_CONFIRM=isolated-target`. The tool refuses a target matching a recorded source host/port/database and refuses nonempty targets. Also check DNS aliases/provider identities manually; string comparisons cannot detect every alias to the same server.

```sh
python3 infra/beta/recovery.py restore \
  --archive /protected-backups/hse-beta-2026-10-24.tar.age \
  --target-root /isolated-recovery/hse-beta
```

The tool restores all databases and files, verifies all service table counts and the HSE evidence digest, and writes `restore-evidence.json`. The restored Moodle config still contains the original connection/origin/secrets: rewrite it for isolated targets before starting Moodle. Use the archived exact Moodle code/plugins, reconfigure Keycloak hostname/client callbacks and app/Moodle URLs, rotate restored credentials, and block all production outbound traffic. Then sign in with dedicated test users, compare profiles, attempts, source completions, manual corrections/voids, and audit history, and confirm that the original environment is untouched. Record actual elapsed recovery, recovery-point time, transactions needing replay, administrator name/date, and browser evidence. File and database checks alone do not prove service sign-in or course playback.

## Local evidence and remaining acceptance

`hse-local-restore-evidence.json` records a completed PostgreSQL-only drill on 2026-10-24 using synthetic fixtures: all 37 public table counts and one evidence packet digest matched in a fresh separate database. It includes completion records and linked correction/void/audit history. It explicitly leaves Keycloak, Moodle/files, and staging recovery pending. Reproduce against an empty target with:

```sh
PATH=/opt/homebrew/opt/postgresql@16/bin:$PATH \
HSE_DATABASE_URL=postgres://localhost/source_synthetic_db \
RESTORE_HSE_DATABASE_URL=postgres://localhost/empty_recovery_db \
BETA_RESTORE_CONFIRM=isolated-target \
python3 infra/beta/recovery.py hse-drill --output-evidence /protected-evidence/hse-restore.json
```

`node infra/beta/verify-alert.mjs` has verified forced failure delivery to a local synthetic HTTP receiver and nonzero failure on a rejected delivery. Receipt by the real named on-call person remains unverified. Docker is unavailable on the implementation machine; GitHub CI has verified production image construction/private startup, synthetic identity/Moodle behavior and encrypted full-stack recovery. Deployment through CI, public TLS, real invitation delivery, the chosen host's recovery configuration and application rollback still require verification on company IT's environment.
