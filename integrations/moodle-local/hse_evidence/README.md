# Moodle completion evidence and identity coordination

Moodle delivers all beta courses. Its core course-completion REST response exposes criterion timestamps, but omits the canonical course timestamp. This optional local plugin exposes the existing `completion_completion::fetch()` record and numeric course grade through Moodle's External Services API. Its evidence endpoint is read-only: it never marks training complete, changes course evidence, or modifies Moodle core.

Install this directory as `public/local/hse_evidence` in each customer's Moodle 5.3 installation and run the supported Moodle upgrade command. Enable `local_hse_evidence_get_completion` in the HSE service's allowlist. The dedicated service account needs `report/completion:view` and `moodle/grade:viewall` in the mapped course; normal Moodle context, active enrollment, user, and group checks also apply. Do not grant a learner this service token.

Set `completionEvidence` to `local_hse_evidence` on that tenant's `MOODLE_CONNECTIONS_JSON` entry. Tokens stay on the HSE server. Without this explicit setting, the adapter continues to report observations without fabricating a completion date. An unavailable plugin, missing capability, mismatched identity, or invalid timestamp fails reconciliation and leaves existing evidence unchanged.

Course grades are normalized from the numeric course total and are not represented as a particular quiz score. Scale grades and absent grades stay null. Attempts and SCORM details continue to use the core SCORM APIs when a verified activity mapping exists. Pass marks, assessment attempts, remediation and course-completion criteria are configured and tested in Moodle before the HSE mapping is published.

Before production, run the plugin's PHPUnit tests on the exact deployed Moodle patch and demonstrate an actual learner's fail, retry, pass, cron aggregation, and unchanged timestamp after synchronization. TypeScript adapter tests exercise the declared response contract; they do not replace deployment verification.

## Coordinated sign-out

`local_hse_evidence_end_user_sessions` is a separately declared **authentication-state write**. It calls Moodle's supported `core\session\manager::destroy_user_sessions()` API and confirms no sessions remain for that worker. It never edits learning records. Add this function to the HSE service allowlist and explicitly grant `local/hse_evidence:endsessions` to its dedicated service role at system context; no standard role receives it automatically. Install/upgrade plugin version `2026102401` or later.

The HSE logout server resolves the current authenticated person's Moodle user through its validated tenant/instance mapping. It must not accept an arbitrary Moodle user ID from the browser. The plugin independently rejects guest, deleted, site administrator, service-account, webservice-auth, and system/user-administration targets. This company-specific Moodle instance remains the service boundary. The operation ends all Moodle sessions for that ordinary worker, including sessions on another device, before identity-provider logout prevents immediate single-sign-on reentry.

The adapter requires the configured plugin and a matching `{userid, ended:true}` response; service or permission failures must be reported as incomplete coordinated sign-out. A local HSE cookie being cleared alone is not proof that a Moodle browser session ended. Test the actual existing Moodle browser session and Keycloak session on the deployed pair. [Supported Moodle session manager](https://github.com/moodle/moodle/blob/MOODLE_503_STABLE/public/lib/classes/session/manager.php).

Primary references: [Moodle completion external service](https://github.com/moodle/moodle/blob/MOODLE_503_STABLE/public/completion/classes/external.php), [canonical completion API](https://github.com/moodle/moodle/blob/MOODLE_503_STABLE/public/completion/completion_completion.php), and [external service development](https://moodledev.io/docs/5.3/apis/subsystems/external/writing-a-service).

## OAuth learner identity bridge

Install/upgrade plugin version `2026102402` or later. `local_hse_evidence_link_oauth_login` creates the explicit issuer/subject binding that Moodle OAuth login needs to reuse an existing REST-provisioned learner. It calls the supported `auth_oauth2\api::link_login()` API with its normal permission checks. It never writes Moodle core tables directly, confirms an email, changes an existing binding, creates a user, or changes completion evidence. Confirmed exact bindings are idempotent; pending, expired, foreign, duplicated, or mismatched bindings require administrator review.

Configure the issuer through Moodle's OAuth services administration, then set **HSE identity bridge OAuth issuer ID** and **HSE identity bridge OIDC issuer URL** under the plugin's administration settings. Both default to disabled. The exact URL, including any trailing slash, must equal the issuer's base URL and the portal's expected OIDC issuer. The issuer must be enabled and available for login, keep confirmation required, map only `sub` to `username` and `email` to `email`, and have no `idnumber` mapping. Enable OAuth 2 authentication and lock its `idnumber` and `email` fields (`field_lock_idnumber=locked`, `field_lock_email=locked`). Preserve the site's account-creation policy; the bridge never relaxes self-registration or issuer confirmation. A beta instance should prevent creation of unprovisioned accounts.

Enable the separately installed **HSE identity bridge** external service (`hse_identity_bridge`). It is disabled by default, restricts authorized users, permits no file transfers, and contains only this one function. Assign a dedicated service user and expiring token. Grant only `webservice/rest:use`, `local/hse_evidence:linkoauth` at system context, and `auth/oauth2:managelinkedlogins` in the target user contexts (or system context for inheritance). The bridge needs no user-administration, site-configuration, enrollment, or learning-record capability. No standard Moodle role receives the custom capability. Configure its token separately as `oauthBridgeToken` in the portal connection; keep the regular Moodle token outside this service.

The request contains `userid`, `hseid`, `subject`, `identityemail`, `issuerid`, and `issuerurl`; success returns only `{userid, issuerid, linked:true}`. The portal must resolve these fields on the server from the active person's tenant/instance mapping and exactly one active principal in its expected OIDC issuer. Do not expose this operation or accept these identity fields from an arbitrary browser request. The Moodle endpoint independently checks the fixed issuer and mappings, exact unique live HSE UUID/idnumber and identity email, local active confirmed `oauth2` account, and absence of system/user administration or bridge privileges on the target. OIDC subjects must fit Moodle's lowercase username representation; Keycloak UUID subjects do. The identity email may be a technical `.login.invalid` address: explicit binding does not use email confirmation, and notification suppression remains a separate provisioning responsibility.

Run `vendor/bin/phpunit --testsuite local_hse_evidence_testsuite` after Moodle's PHPUnit setup. The bridge tests cover least privilege, immutable metadata, stale/conflicting identity links, issuer mapping/configuration, notification absence, and preservation of the user and canonical course completion record. Also prove actual Keycloak-to-Moodle browser login through this endpoint on the deployed patch, using a REST-provisioned technical-email account, and verify the session's Moodle user ID and stable HSE idnumber. PHPUnit and a successful REST link alone do not prove browser SSO.

Primary references: [supported linked-login API](https://github.com/moodle/moodle/blob/v5.3.0/public/auth/oauth2/classes/api.php), [OAuth login binding and confirmation behavior](https://github.com/moodle/moodle/blob/v5.3.0/public/auth/oauth2/classes/auth.php), and [supported OAuth configuration API](https://github.com/moodle/moodle/blob/v5.3.0/public/lib/classes/oauth2/api.php).
